# Compatibility

Streamlit runtime compatibility is pinned to 1.66.1. Product scope follows the official documentation catalog captured in the ignored cache `target/upstream/docs`; its observed docs label is 1.66.0 and its runtime target is 1.66.1. Version labels are recorded separately and no inaccessible versioned URL is synthesized.

The only feature matrix is [compatibility/api-compatibility-matrix.json](../compatibility/api-compatibility-matrix.json). It currently records 182 captured canonical pages, not a claim of completeness: 7 requested legacy pages are unavailable in the current docs and 2 redirects are recorded as aliases rather than extra rows. Missing and redirected pages stay explicit in the matrix and [p0-baseline.json](../compatibility/p0-baseline.json).

Each row has an official URL, Rust plan, `implementation_status`, `compatibility_status`, and evidence links. Read the current matrix for evidence-backed progress; source candidates and same-name function counts do not establish implementation or compatibility. Verification must compare Rust API behavior, HTTP/WS/protobuf traces, and the unmodified official frontend against the pinned Python reference.

`python tools/verify_p0.py` regenerates the matrix while preserving prior evidence-backed non-unverified statuses when a row remains the same. New catalog rows and rows without sufficient evidence remain unverified.

The native input-widget implementation provides a session-local registry for selectbox string wire values, slider double arrays (including integer sliders), checkbox booleans, and one-run button triggers. All incoming values are applied before synchronous callbacks, then main executes. Explicit keys bind native JSON state; keyed slider bounds/step changes reset identity and unrendered widgets undergo end-of-run cleanup. Native unit and real HTTP/WS tests cover these contracts, callback ordering, ordinary reruns, retained-session recovery, fresh-session reset, and concurrent-session isolation. The prior closed-loop Python raw establishes those value types only: it does not expose full server parameters. The eight real Chrome widget cases now drive a Rust full-element differential test: defaults/options, explicit key seeding, disabled fields, None option versus empty selection, first-element retention on duplicate key, and observed callback order. Only opaque ID digests are normalized; digest shape, key suffix and within-session stability remain checked. The test compares optional presence, values, width and one-shot fields through protobuf encoding. Python duplicate-key capture emits StreamlitDuplicateElementKey and finishes with status 0; Rust currently exposes a fallible WidgetError, and an application that unwraps it does not have equivalent exception UI/termination behavior. That remains an explicit gap rather than a passed negative UI case. The measured widget subset and final captures have passed independent review; per-feature status remains tracked in the matrix rather than inferred as complete compatibility. Scope follows the official [selectbox](https://docs.streamlit.io/develop/api-reference/widgets/st.selectbox), [slider](https://docs.streamlit.io/develop/api-reference/widgets/st.slider), [checkbox](https://docs.streamlit.io/develop/api-reference/widgets/st.checkbox), and [widget lifecycle](https://docs.streamlit.io/develop/concepts/architecture/widget-behavior) documentation, not Python implementation analysis. Outstanding capabilities include the temporal slider types below, new selectbox options/filter configuration, query binding, persistent hidden widgets and full lifecycle edge parity; stop/cancel and data views remain separate gaps.

The disabled reference case records attempted clicks on selectbox and checkbox with zero subsequent frames; slider has only its `disabled` wire field verified, not an attempted disabled interaction. These Python observations do not establish Rust disabled-interaction behavior. The fresh-tab [Rust six-widget capture](../tests/browser/rust-widgets/trace-widgets.json) records 6/6/6 expected/executed/asserted cases; the [Python numeric reference](../tests/reference/reference-browser/numeric/trace-widgets-numeric.json) records 4/4/4. Both were recaptured with real request IDs and connection identities, successful actions, changed target values and matching returned DOM values. Final independent review passed for these captures and the corrected collector counterexamples; no earlier candidate or incorrectly scoped probe establishes acceptance. The four numeric fullElement shapes match apart from opaque ID digests, including float format/data type and range defaults. This measured subset does not establish all numeric options or full execution compatibility. Replay commands stay in the [browser test README](../tests/browser/README.md).

Slider type coverage and remaining native API work:

| Official value type | Rust counterpart / current result | Remaining evidence or implementation |
|---|---|---|
| Integer | `SliderOptions<i64>` or `<i32>`; scalar native/WS tests | `i32` bounds must fit `i32`; both obey JS-safe integer limits. Captured configuration has wire/DOM comparison; independent review passed for the measured configuration. |
| Float | `SliderOptions<f64>`; scalar native/WS tests | Default numeric limits 0..1 and step 0.01 implemented; captured format and UI comparison independently reviewed for the measured configuration. |
| Two-element numeric tuple/list | `(T, T)` or `[T; 2]` for the above scalar types; native/WS round trips | Exactly two endpoints, with original native return shape; nested ranges rejected at compile time. Captured ranges have wire/DOM comparison; independent review passed for the measured configuration. |
| Date | Planned `SliderOptions<chrono::NaiveDate>` | Not implemented. Docs give value ±14 days, daily step and epoch-microsecond storage; need real wire/returned-date/precision-bound observations. |
| Time | Planned `SliderOptions<chrono::NaiveTime>` | Not implemented. Docs give full-day bounds and 15-minute step; epoch anchor, fractional precision and timezone handling need observation. |
| Datetime | Planned naive `chrono::NaiveDateTime`; offset-aware form needs its own reference | Not implemented. Docs give value ±14 days and conditional daily/15-minute step. Do not choose UTC/local/DST/offset conversion without an oracle. |
| Temporal two-element tuple/list | Planned pair or `[T; 2]` of the temporal scalar type | Not implemented. Requires typed temporal bounds, `chrono::TimeDelta` steps, reversible codecs and temporal identity constraints; do not coerce these through current numeric bounds. |

Reuse the workspace's existing `chrono` dependency (locked 0.4.42 with serde), with no additional crate or lock update needed for that design. Public temporal options must preserve their native type in session state and callbacks while the codec emits the official Slider data type and checked microseconds. The exact conversion is intentionally unimplemented until observed. Numeric constructors currently require an explicit initial value; docs' omitted-value behavior maps to passing the lower bound, with a future typed convenience constructor still outstanding. Format strings are passed to the official frontend without changing returned numeric values; this does not establish every predefined/printf format's parity. Cleanup currently covers ordinary unrendered-widget removal, key recreation after deletion, and unrelated manual-key retention; manual self-assignment/cleanup exceptions and persist-state/query binding remain unverified or absent, not complete lifecycle support.

The retained [Rust button smoke](../tests/browser/rust-smoke/trace-smoke.json) exercises the official frontend at `127.0.0.1:8501`: 36 frames, three true button triggers each followed by a successful completion on the same connection, and HTTP 200 for `/`, health, host-config, and favicon. `tests/browser/rust-smoke/` is persistent Rust UI evidence; Python oracle captures remain under `tests/reference/`. The frozen Rust raw retains an incorrect inherited `scope` string saying “PYTHON SIDE ONLY”; its URL, Rust NewSession name, and observed heading identify the actual Rust run. This smoke is limited to the button demo and does not prove general API compatibility; current per-feature progress remains recorded in the matrix.

Known security-handshake gap: the Rust run sets no `_streamlit_xsrf` cookie, the official frontend sends `streamlit, PLACEHOLDER_AUTH_TOKEN`, and the Rust server performs no XSRF validation. A successful WebSocket connection therefore does not establish security-handshake compatibility or production readiness. Session IDs are reconnect handles, not authenticated user identities; application code must not treat possession of one as authorization.

The native session batch adds typed JSON application values, rerun persistence and retained-session recovery. Real Rust HTTP/WS regressions against a two-worker server cover ordinary reruns, valid-ID reconnect with a subsequent increment, fresh-session reset, two simultaneous sessions, and non-sticky button triggers. The official browser reference probe accepts an unknown UUID and the opaque string `unknown-session` with HTTP 101 and successful completion, returning a new server-selected ID; a known-ID lookup returns that same ID. Rust follows those observed lookup rules without UUID-format rejection or an active-session 409. Versioned ownership prevents an old connection's Drop from expiring its replacement. The reference fate of an original socket during a known-ID lookup remains unmeasured, and this is not complete takeover compatibility. Expiry/retention is still a local policy pending a TTL-specific reference observation. The session core, controlled-await ownership boundary, and final [S1 browser counter evidence](../tests/browser/rust-counter-s1/trace-counter.json) have independently passed review for the measured subset: four click windows, same-ID recovery followed by 2→3, fresh-ID reset to 0, and two-tab isolation. The capture has three complete handshakes across four observed connections; tab B's initial handshake is missing, but its distinct NewSession ID is recorded. That original session-only milestone did not cover widget-key association or callbacks; the current input-widget coverage is described above. Stop/cancel and full execution semantics remain gaps.

The frozen static status implementation covers `info`, `warning`, `error`, and `success` using official Alert messages. Its eight Rust tests cover the four defaults; explicit icon/width/title and middle-body emoji; leading icon extraction and explicit empty icons; compound emoji and a leading ZWJ cluster; rejection of two independent emoji; additional Rust Unicode boundaries; the observed invalid-width error; and Rust parameter/Markdown boundaries. The first measured examples are backed by the Python [base](../tests/reference/reference-browser/status/trace-status.json), [leading-icon](../tests/reference/reference-browser/status/trace-status-leading.json), and [compound-icon](../tests/reference/reference-browser/status/trace-status-icon-composite.json) captures. Additional Rust-only Unicode boundary tests do not prove upstream acceptance parity for the full Unicode repertoire. The status implementation, required dependencies, and final [Rust browser status evidence](../tests/browser/rust-status/trace-status.json) have independently passed review for the measured subset: 17 rendered alerts, 16 uniquely matched oracle comparisons, 240 px fixed width, relative stretch, and the captured compound-emoji cases. The current matrix records the accepted limited progress as partial, without claiming full Unicode or API compatibility.
