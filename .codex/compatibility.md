# Compatibility

Streamlit runtime compatibility is pinned to 1.66.1. Product scope follows the official documentation catalog captured in the ignored cache `target/upstream/docs`; its observed docs label is 1.66.0 and its runtime target is 1.66.1. Version labels are recorded separately and no inaccessible versioned URL is synthesized.

The only feature matrix is [compatibility/api-compatibility-matrix.json](../compatibility/api-compatibility-matrix.json). It currently records 182 captured canonical pages, not a claim of completeness: 7 requested legacy pages are unavailable in the current docs and 2 redirects are recorded as aliases rather than extra rows. Missing and redirected pages stay explicit in the matrix and [p0-baseline.json](../compatibility/p0-baseline.json).

Each row has an official URL, Rust plan, `implementation_status`, `compatibility_status`, and evidence links. Read the current matrix for evidence-backed progress; source candidates and same-name function counts do not establish implementation or compatibility. Verification must compare Rust API behavior, HTTP/WS/protobuf traces, and the unmodified official frontend against the pinned Python reference.

`python tools/verify_p0.py` regenerates the matrix while preserving prior evidence-backed non-unverified statuses when a row remains the same. New catalog rows and rows without sufficient evidence remain unverified.

The retained [Rust button smoke](../tests/browser/rust-smoke/trace-smoke.json) exercises the official frontend at `127.0.0.1:8501`: 36 frames, three true button triggers each followed by a successful completion on the same connection, and HTTP 200 for `/`, health, host-config, and favicon. `tests/browser/rust-smoke/` is persistent Rust UI evidence; Python oracle captures remain under `tests/reference/`. The frozen Rust raw retains an incorrect inherited `scope` string saying “PYTHON SIDE ONLY”; its URL, Rust NewSession name, and observed heading identify the actual Rust run. This smoke is limited to the button demo and does not prove general API compatibility; current per-feature progress remains recorded in the matrix.

Known security-handshake gap: the Rust run sets no `_streamlit_xsrf` cookie, the official frontend sends `streamlit, PLACEHOLDER_AUTH_TOKEN`, and the Rust server performs no XSRF validation. A successful WebSocket connection therefore does not establish security-handshake compatibility or production readiness. Session IDs are reconnect handles, not authenticated user identities; application code must not treat possession of one as authorization.

The native session batch adds typed JSON application values, rerun persistence and retained-session recovery. Real Rust HTTP/WS regressions against a two-worker server cover ordinary reruns, valid-ID reconnect with a subsequent increment, fresh-session reset, two simultaneous sessions, and non-sticky button triggers. The official browser reference probe accepts an unknown UUID and the opaque string `unknown-session` with HTTP 101 and successful completion, returning a new server-selected ID; a known-ID lookup returns that same ID. Rust follows those observed lookup rules without UUID-format rejection or an active-session 409. Versioned ownership prevents an old connection's Drop from expiring its replacement. The reference fate of an original socket during a known-ID lookup remains unmeasured, and this is not complete takeover compatibility. Expiry/retention is still a local policy pending a TTL-specific reference observation. The session core, controlled-await ownership boundary, and final [S1 browser counter evidence](../tests/browser/rust-counter-s1/trace-counter.json) have independently passed review for the measured subset: four click windows, same-ID recovery followed by 2→3, fresh-ID reset to 0, and two-tab isolation. The capture has three complete handshakes across four observed connections; tab B's initial handshake is missing, but its distinct NewSession ID is recorded. Automatic widget-key association, callbacks, stop/cancel, and full widget/execution semantics remain outside this batch.

The frozen static status implementation covers `info`, `warning`, `error`, and `success` using official Alert messages. Its eight Rust tests cover the four defaults; explicit icon/width/title and middle-body emoji; leading icon extraction and explicit empty icons; compound emoji and a leading ZWJ cluster; rejection of two independent emoji; additional Rust Unicode boundaries; the observed invalid-width error; and Rust parameter/Markdown boundaries. The first measured examples are backed by the Python [base](../tests/reference/reference-browser/status/trace-status.json), [leading-icon](../tests/reference/reference-browser/status/trace-status-leading.json), and [compound-icon](../tests/reference/reference-browser/status/trace-status-icon-composite.json) captures. Additional Rust-only Unicode boundary tests do not prove upstream acceptance parity for the full Unicode repertoire. The status implementation, required dependencies, and final [Rust browser status evidence](../tests/browser/rust-status/trace-status.json) have independently passed review for the measured subset: 17 rendered alerts, 16 uniquely matched oracle comparisons, 240 px fixed width, relative stretch, and the captured compound-emoji cases. The current matrix records the accepted limited progress as partial, without claiming full Unicode or API compatibility.
